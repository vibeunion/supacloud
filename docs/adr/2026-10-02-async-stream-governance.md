## 2. 背景与非目标

采用朴素的业务模型、明确的模块边界和可验证的治理职责，减少不必要的订阅、调度与隐式副作用。
框架为同类任务提供清楚的推荐路径，不以框架 API 数量或是否引入某个库衡量企业级程度。

这是一项工程取舍，不是已完成的 AI 准确率实验。不得宣称 Schema 能保证业务正确、某种语法
天然没有泄漏，或没有评测就给出生成准确率。协议正确性、权限、并发与资源所有权需要独立验证。

本 ADR 不要求重写 Angular、替换原生 Supabase／SupaCloud 客户端、发明新的 DI／工作流／
Schema 系统、追踪全部全局 Promise，或新增未经审查的生产诊断 HTTP 端点。
本次文档变更不修改运行时代码、依赖、公开签名、权限、数据库、部署或版本发布行为。

## 3. 核心决议

### 3.1 单次业务：明确契约与 async/await

**ASYNC-01**：新生成的异步 Command、普通 Query 和跨模块异步 Service 使用明确的输入／输出
契约和 `Promise<TResult>`。纯计算、同步验证仍可以返回 `T`，不为形式统一制造异步。
现有框架 hook／切面中的 `T | Promise<T>` 兼容签名不由本 ADR 追溯性删除；新的业务模板
不得据此引入多值 Observable 作为单次业务完成模型。

**ASYNC-02**：业务完成是约定的执行与持久化边界完成，不是创建 Promise、流或订阅对象。
调用者必须等待工作，或把工作移交给有明确 owner、失败观察与退出规则的宿主。
定时器、监听器、连接与异步任务分别拥有取消、超时和释放规则；函数返回与 GC 不替代清理。
`AbortSignal` 和 `PendingWorkRegistry` 是显式协作机制，不是自动取消或自动回滚的证明。

**ASYNC-03**：单次 Command 不得因返回 Observable、AsyncIterable 或其他未执行流对象而被记录
为已成功完成。静态检查应识别真实类型／符号来源，而不是仅检查某个对象是否名为 `subscribe`。
运行时必须按结果契约验证；非 TypeScript 调用和类型逃逸也要有反例。框架不得偷偷订阅返回流
来猜测“一次业务”的完成点。显式流式端点按第 3.2 节处理，不混用这项单次结果契约。

输入与输出应复用既有 Schema／契约来源；静态推导与外部数据的运行时验证并存。
输出校验失败可能发生在持久化之后，不得自动标记为已回滚或重发写入；通过权威回执核对结果。

### 3.2 持续输出：标准事件与字节边界

**STREAM-01**：持续业务事件消费优先使用 `AsyncIterable<TEvent>`；HTTP 字节传输使用
`ReadableStream<Uint8Array>` 或原生 `Response`。适配时保持业务事件、编码字节和传输状态分层。
这些类型不自动提供投递保证、持久化、广播、重连、业务确认或资源关闭。

每个公开流协议必须说明：

- owner 与创建时机；信号取消、提前结束迭代、异常和正常完成时的资源释放行为。
- 排序、事件标识、游标范围与保留期；重复、缺口、过期游标与权限撤销如何处理。
- 缓冲项数、缓冲字节数和单消息上限；慢消费者触发合并、拒绝、断开还是持久化。
- 重连是否重新鉴权；读取重试与业务写入重试的区别；最长等待和资源排空的超时处理。
- 是否需要业务 Ack/Nack；需要时，确认时机、失败后重投与重复处理责任由谁承担。

**STREAM-02**：不要求每个流都新增 Ack/Nack 方法。界面状态快照可以没有业务确认；可靠任务
输出必须保留原协议的确认规则。收到 `next()`、取得 `reader.read()` 的值或从迭代器取得事件，
都不得被通用适配器擅自升级为“业务处理完成”。协议若把继续迭代视为确认，消费者必须完成
本次处理后才能继续拉取，适配器不得预读并提前确认。

**STREAM-03**：遵守底层源是否真正支持暂停／取消的能力约束。无法暂停的推送源必须有明确的
过载策略，不能用一个 `ReadableStream` 外壳宣称端到端背压。缓冲只限制项数时必须明示，
不得把它当成完整内存上限；有损合并只适用于明确允许丢弃中间状态的协议。

**STREAM-04**：流式连接的生命周期与业务事务分离。已发送 HTTP 响应不保证 request scope
仍然有效；不得默认延长事务以等待整个流消费。确实需要游标事务或长连接的专用端点，必须
声明所有权、预算、超时和连接回收验收。释放借用资源不得误关其他请求共享的连接池。

停止客户端观察、取消协作 I/O、取消服务器任务和撤销已发生的外部副作用是四个不同动作。
观察结束不得隐式调用业务 `cancel`／`retry`／重新提交。无法确认的结果保持未知状态。

### 3.3 RxJS：官方支持的场景化集成

**RX-01**：RxJS 用于复杂事件组合和明确选择的生态适配，不是全系统默认业务语言。
多源合并、时间窗口、去抖等内部逻辑可以直接复用 RxJS，不为避免依赖而重复自研操作符。

**RX-02**：通用业务契约、核心执行入口和纯领域逻辑不得反向依赖 RxJS 或响应式适配层。
明确选择的 `/reactive`、`/rxjs`、`/angular` 等专用入口可以公开 Observable 和该生态的原生类型。
依赖方向是“响应式适配器使用核心契约／执行能力”，不是反过来。

**RX-03**：订阅必须有明确 owner。禁止未受管的隐式订阅、自动重订阅业务写入和跨项目共享
敏感回放缓存。专用适配 API 必须说明订阅何时开始、重复订阅的效果、取消语义和错误通道；
例如显式选择的 `toSignal` 可以按其文档立即订阅，不能把这类已声明行为误判为禁止事项。

不选用响应式入口的业务代码不需要直接配置、导入或理解 RxJS；但这不等于当前安装图没有
RxJS。过渡期保留已有依赖和导出。真正的“核心安装图不含 RxJS”是依赖拆分后的独立验收目标，
只有干净消费者安装、类型和运行时依赖图验证后才可宣称达成。

### 3.4 业务治理：受控调用，不是万能沙盒

**GOV-01**：身份凭据验证与可信身份上下文由既有认证组件和可信宿主承担。
`@supacloud/app/execution` 消费明确的调用上下文和治理适配器，负责受控执行组合、授权与
幂等／事务／审计能力的接入。不能根据包名或装饰器推定已验证令牌，也不得从未验证的头部
或业务入参构造可信租户身份。幂等回放仍需重新授权。

**GOV-02**：执行管线不是恶意代码隔离沙盒，不能约束业务自行获得的管理员连接或任意网络
能力。应用代码应使用项目绑定、受限凭据和受管外部调用接口。按威胁模型使用数据库 RLS／
受限角色、进程／容器及网络策略等纵深防御，验证高权限角色和其他旁路；这些机制不因被写进
文档就自动生效，也不要求每个纯函数都套一层容器。

**GOV-03**：本地数据库事务不能推导外部副作用已撤销。跨系统流程按具体协议选择可靠投递
（如事务性 outbox）、幂等、权威回执对账、Saga／显式补偿或人工处理，不强制统一引入一种引擎。
补偿本身也是可能失败或结果不确定的业务动作；不得把“已发送补偿”记为“已成功撤销”。

**GOV-04**：警告日志不能替代控制。不确定的提交／外部结果应保持可追踪的未知状态，禁止
盲目自动重发；是否可重试由权威协议、稳定操作标识及适配器保证决定。缺失必需能力时拒绝
执行，不能靠给一个无实际能力的适配器标记 `true` 来通过验收。

### 3.5 SupaCloud JS：保持一套客户端与一套治理规则

**SDK-01**：复用 `createSupaCloudClient()` 的现有客户端。Database／Auth／Storage 继续使用
`client.supabase`；平台 commands／tasks／functions 等保持既有 API、认证、项目绑定和返回协议。
本 ADR 不统一重写 SDK 错误信封，不把原生 PromiseLike 查询链强制包装为第二个 HTTP 客户端。

`observeQuery()`、`observeTask()` 继续留在明确的 `@supacloud/js/reactive` 集成入口。
任务先通过原 API 提交一次，再观察已有回执；重复观察和停止观察不得重复提交、取消或重试
服务器任务。查询工厂每次订阅会重新执行，所以不得用它隐藏写入重放。

`@supacloud/js/task-events` 的持久化输出继续沿用其 `watch`／异步迭代协议和处理游标规则。
未经确认语义验收，不得直接用 `from(watch(...))` 把拉取消费改为推送消费。

## 4. 架构分层与实际入口

| 层次 | 推荐契约 | RxJS 边界 |
| --- | --- | --- |
| 领域纯计算与验证 | `T`／验证结果 | 不依赖 RxJS |
| 新异步 Command／Query／跨模块业务 Service | `Promise<TResult>` | 通用接口不使用 Observable |
| 持续业务事件消费 | `AsyncIterable<TEvent>` | 消费方不被强制引入流库；确认规则另行声明 |
| HTTP 字节传输 | `Response`／`ReadableStream<Uint8Array>` | 使用标准传输边界 |
| 内部复杂事件组合 | 内部操作符／状态逻辑 | 允许局部使用，对业务边界适配 |
| 专用响应式／Angular 入口 | `Observable<T>`／生态原生类型 | 明确选用后允许公开 |
| 治理与事务切面 | 显式上下文和受控 continuation | 不依赖特定流操作符，保留同步／Promise 兼容 hook |

核对基线没有 `@supacloud/app/core` 这个公开子入口。架构检查必须绑定真实路径和 export map：
`@supacloud/app/execution`、`@supacloud/app/contracts`、`@supacloud/contracts` 及实际通用契约入口，
而不是为迁就规范名称新建一套 core。具体保护清单必须在实施时核对。

`@supacloud/app` 根入口已有 Angular 运行时依赖，不能把根包全部模块都当成“零 RxJS 安装图”
进行误报。检查应区分源码依赖、类型声明依赖、构建后运行时依赖和包管理器安装依赖。

### 5.1 诊断与 AI 修复职责

沿用实际 CLI 的 doctor／inspect／编译分析能力和版本支持的参数，不为文档例子制造不存在的
`supacloud doctor --format=json` 等可执行承诺。实现时以该版本 help、源码和消费者测试核对命令。

安全、确定性的修复必须具备稳定规则、预览、显式写入、并发修改检查、幂等执行与回滚说明。
权限策略、事务边界、数据迁移和副作用补偿不凭模型猜测自动决定；呈现上下文，由开发者或
经过审查的流程选择。诊断可能在副作用已发生后出现，修复工具不能据此重放业务。

输出应只包含排障所需元数据，不泄漏令牌、凭据、SQL 参数、请求正文或用户数据。
测试成功仅证明实际覆盖的条件；基线例外与跳过项必须单列，不能把“没有新增诊断”说成
“所有声明零错误”，也不能把模拟网络测试说成真实生产集成验收。

### 5.2 兼容性、例外与回滚

不得在文档 PR 中删除现有公开入口、改变错误信封、切换 Signals 调度或移除必需依赖。
`@supacloud/rx` 等独立包只是待评估方案，不是本 ADR 新增的包或承诺的最终名称。

需要偏离默认模型时，在对应 PR 记录场景、入口边界、owner、错误／取消／重试语义、资源上限、
不影响通用消费者的证据及复核条件。例外不是绕过鉴权或降低 CI 的授权。

后续主版本的破坏性调整须有清单、迁移说明和旧调用的处理策略；具体迁移支持周期另行决策。
模板调整只影响新生成内容，不重写已有项目。已运行的源码迁移通过版本控制恢复；数据库或
外部副作用不能用 git 回退来撤销。撤销本次文档提交仅撤销规范记录，不改变既有运行时。

## 6. 取舍与成功标准

不采用“全系统 Observable 化”，也不采用“全面禁止 RxJS”。前者会把订阅与调度责任扩大到
无需事件组合的业务；后者会让专用生态集成重复实现适配。两项代价均按实际项目验证，不编造
普遍的性能或 AI 失误率结论。

保留的代价是过渡期安装图仍有依赖、专用集成仍需维护，以及标准流协议必须自己写清责任。
收益目标是核心调用不要求响应式知识、SDK 行为不分叉、错误能定位、资源与副作用可核验。

Vibecoding 验收采用固定模型／版本、相同上下文预算和代表性任务，记录首轮验收通过率、
修复轮数、人工审查成本，以及重复写入、越权、泄漏和确认过早等缺陷；未执行评测不报告数字。
规范台账全部结项、发布消费者通过和生产场景验收是不同里程碑，不得合并成“已全部完成”。
