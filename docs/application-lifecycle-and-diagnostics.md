## 1. 核心判断与演进目标

应用生命周期不再是当前 P0，也不高于集群管理员隔离残留。Elysia 应用对象已经按模块顺序初始化、逆序销毁，启动失败会回滚已初始化模块，关闭钩子失败后会继续清理其余资源。还没补上的是编译生成的 `onInit` 回滚、injector 路径不排空 HTTP，以及 `fetch()` 的关闭过程。这些缺口属于 `@supacloud/app` / Elysia。

评估结论概括为：
1. **应用级资源生命周期退出 P0。** 上面四项已经在 Elysia 应用对象上。剩余缺口是编译生成的 `onInit` 回滚、injector 路径不排空 HTTP，以及 `fetch()` 关闭。诊断来源标记（source / artifact / runtime）仍是应用车道以后的可选项，不是当前工作。
2. **两项按需参考与整理**：开发体验/命令统一与 WebSocket Gateway。Realtime 保持现有 Elixir 通道，加上现有 outbox / 任务状态。协议限制可以以后再测。这里不新开事件源，也不把新的 Realtime 协议写成当前工作。
3. **架构底座决策**：以**借鉴业界成熟模式为主，暂不整体以第三方通用框架为底层底座**；同时对内审视并收缩自研通用框架范围，避免无边界扩张。

## 2. 排除项：已有能力避免重复建设

核对当前仓库后，以下能力在 SupaCloud 中已经具备对应基础，不应再列为新增功能而重复建设：

| 参考方向 | SupaCloud 当前基础 | 评估判断 |
| --- | --- | --- |
| **整套 Resource 生成** | 已有 Model、Service、Controller、Module 生成及配套测试，支持显式父模块注册（`--register-in`） | 不需要另起一套生成器 |
| **生成前预检、冲突检测与受控恢复** | 已覆盖项目相对路径、符号冲突、文件冲突及受控清理回滚，明确不是崩溃原子的文件事务 | 保持现有回归测试，不另造事务系统 |
| **打包后的真实使用验收** | 已在工作区外安装候选打包 CLI，生成、检查、构建并启动完整应用进行 loopback 验收（`check_app_generation.ts`） | 验收通道已建立且接入 CI 门禁 |
| **原生 Elysia 插件与类型保留** | 已有 HTTP 插件组合、上下文推导、模块服务类型保留及隔离测试 | 不需要再额外包装一层插件框架 |
| **结构化应用理解** | 已有 `context`、`doctor`、`graph`、`inspect` 以及共享 DevTools 协议 | 重点在提升解释准确性，而不是再造工具 |

前三项已在 [Application Generation](./application-generation.md) 中详细说明；原生 HTTP 类型组合也已进入适配器。因此，后续判断标准应是：**能否消除真实故障或开发阻力，而不是继续增加框架名词。**

## 3. 待补强方向与实施路线

### 应用级资源生命周期（不再是 P0）

#### 背景与现状差距
业界成熟框架对生命周期给出了清晰约定：
- 模块按依赖顺序拓扑初始化、反向拓扑销毁；
- 异步初始化会被显式等待；
- 关闭时某个钩子失败，不阻断其他资源清理；
- 即使应用只通过 `handle()` 或 `fetch()` 接收测试请求、从未实际监听端口，也可以执行关闭钩子；
- **生命周期按实例去重，而不是按 provider 注册项调用**：同一个连接池或服务实例通过别名或多重模块导出被多次引用，不会导致重复初始化或二次关闭。

Elysia 应用对象（`@supacloud/elysia` 的 `createApplication`）已经做到其中四件：模块按给定顺序初始化、逆序销毁、启动失败时回滚已初始化模块，以及某个 `destroyServices` 失败后继续清理其余模块。编译模块契约另有请求与任务作用域：
- `createServices(...)`
- `createRequestScope(...)` / `destroyRequestScope(...)`
- `createJobScope(...)` / `destroyJobScope(...)`

**还没补上的缺口更窄**：编译生成的 `onInit` 在中途失败时，生成代码自己不回滚已经成功的实例；injector 路径（`bootstrapBun`）不排空 HTTP；只通过 `fetch()` 调用、没有监听端口时的关闭过程仍未收口。这些属于 `@supacloud/app` / Elysia，不高于集群管理员隔离残留：`supabase_auth_admin` / `supabase_admin` 仍是集群级 LOGIN，并可 CONNECT 到每个租户库。不要再把“应用级启动与退出整体缺失”写成当前差距。

典型现实场景：
```text
数据库连接池 (DB Pool)
       ↓
    订单服务 (OrderService)
       ↓
订单订阅器 / 后台消费者 (Queue Consumer)
```
- **启动时**：必须在连接池就绪后才启动依赖它的后台消费者；
- **关闭时**：必须先停止接收新请求/任务、排空在途任务，最后才释放数据库连接池；
- 否则，“每个组件都有 `close()`”也不等于应用能够可靠退出。

#### 实施建议
不把已经存在的模块顺序、逆序销毁、启动回滚和关闭失败后续清理重新立项，也不另造第二套运行时 DI 容器：
1. **静态计划**：Elysia 应用对象已经按给定模块顺序执行。编译依赖图再生成一套初始化序列不是当前工作；
2. **实例去重与所有权**：运行宿主执行清理时基于实例集合去重，并严格区分“应用创建并负责释放的资源”与“外部宿主传入、仅借用的资源”，禁止无差别调用 `close()`；
3. **失败回滚**：模块级启动回滚和关闭失败后继续清理已经在 Elysia 应用对象上。还没做的是编译生成的 `onInit` 中途失败时回滚已成功实例；
4. **测试与排空**：injector 路径仍不排空 HTTP。`fetch()` 关闭过程仍是缺口，不要把它写成已经完成。

### 诊断来源标记（以后的可选项，不是当前工作）

source / artifact / runtime 标记属于以后的应用车道可选项。下面保留当时的对照，不把它写成当前工作。

#### 背景与现状差距
优秀的诊断系统通常将几个关键事实分开报告：启动采用的模块图、实际挂载的路由、采用的构建产物，以及构建阶段对静态生成的判断。声明过的路由不一定等于当前进程实际服务的路由。

SupaCloud 同样存在三种状态维度：
- **源码视图**：按当前声明重新编译，理论上应该得到什么？（如 `bun run inspect`）
- **产物视图**：磁盘上当前保存的编译结果包含什么？（如 `app graph` / `app explain`）
- **运行视图**：当前进程实际加载了什么产物、挂载了哪些原生路由与扩展？

**差距在于**：当前这一区别主要体现在文档说明中，工具本身缺乏显式的机器可读来源标识。当开发者遇到“改了源码但未执行编译”或“产物重新编译但本地服务未重启”时，排查往往依赖人工经验。

#### 实施建议
在现有的 `context` / `graph` / DevTools 协议内实现小范围闭环：
1. **元数据标记**：在诊断输出中增加结果来源（`source: 'source' | 'artifact' | 'runtime'`）、构建与产物标识哈希，以及运行进程实际载入的产物信息；
2. **分类报告**：明确区分静态声明能力、原生 Elysia 插件扩展追加的能力，以及未覆盖分析的部分，不把“无法静态分析”伪装成“已检查通过”；
3. **漂移检测**：在 `app check` / `doctor` 中对“源码哈希与产物记录不一致”、“产物时间戳落后于源码”提供精确诊断代码；
4. **安全与协议演进**：
   - 语义变更时严格升级 DevTools 协议版本，保持向后兼容性验证；
   - 坚持保守采集策略：开发诊断不默认抓取业务 Payload 正文，敏感字段统一脱敏，避免企业多租户环境下的凭据或数据泄露。

### P2：开发体验与命令认知统一

#### 背景与现状差距
极简脚手架体验通常以“创建应用 → 添加资源 → 构建 → 启动 → 验证接口”的极简闭环展开，并清楚说明生成的存储属于内存实现、重启即丢失，让开发者对安全边界有明确预期。

SupaCloud 的资源生成器在安全上更严格：生成的 Service 默认主动拒绝执行，直到开发者接入合法的持久化端口；写操作强制引导至受治理的 Command，杜绝生成虚假的 CRUD 产生安全错觉。这种企业级安全边界必须保留。

**差距在于**：
- 入口命令认知在文档中有混淆（`supacloud` 为当前 CLI 入口，而部分愿景文档仍写作 `supacloud`）；
- 现有生成的 Resource、Command、客户端契约与业务示例缺乏一条连贯、可验证的“首次使用教程”。

#### 实施建议
1. **统一文档命令**：在面向开发者的文档和生成器输出中统一使用 `supacloud`，明确 `supacloud` 服务端二进制的边界；
2. **串联黄金链路**：整理现有的 fulfillment 示例，编写涵盖 Resource 读操作、Command 写操作、Worker 消费及客户端调用的端到端说明；
3. **标清边界**：在脚手架注释中清楚注明“演示占位代码”与“生产所需对接”，指导开发者安全替换占位符。

### 按需参考：WebSocket Gateway

#### 评估分析
长连接网关设计具备合理的职责边界：应用层负责事件与处理器的映射、依赖注入与生命周期，底层的 Bun / Elysia 负责连接管理、协议升级、订阅发布和背压。

**当前判断**：
- Realtime 保持现有 Elixir 通道，加上现有 outbox / 任务状态。协议限制可以以后再测。
- 这里不描述新的事件源，也不把新的 Realtime 协议写成当前工作。装饰器发现的事件目前无法直接进入静态客户端类型体系。
- **不做**。不为对齐概念而新开应用层 WebSocket 网关。

## 4. 架构底座决策：自研收敛 vs 引入外部通用框架底座

### 核心结论
**以自研极简静态编译体系为主，暂不整体引入第三方通用框架作为底层底座。**

### 权衡考量

#### 1. 替换底座能减少的代码有限
若引入外部框架接管通用应用层，看似分工明确：
```text
通用应用框架：负责通用模块、DI、Controller、路由、生命周期
       ↓
SupaCloud 扩展：负责架构检查、持久化治理、业务契约、执行管线
       ↓
SupaCloud 平台：负责多租户基础设施与应用托管
```
看似节省了通用框架代码，但在实际落地中：
- **编译模型冲突**：外部框架通常依然采用运行时创建容器、解析实例的模式；SupaCloud 编译器则基于 AST 直接生成无反射的静态装配代码，并承担持久化治理策略与数据库契约检查。若强行将其改造为静态代码生成，将深度侵入外部框架核心。
- **作用域模型冲突**：多数外部框架核心模型为单例（Singleton）；SupaCloud 严格区分 `application`、`request` 与 `job` 作用域。即使能通过改造注入上下文，也会导致 fork 与上游完全脱节。
- **最难维护的代码仍由我们负责**：多租户身份绑定、事务性 Command 执行、幂等回执、业务审计与不可变物料追溯，无法由通用框架代劳。因此，引入并维护外部底座 fork 的额外成本很可能大于其节约的通用代码。

#### 2. 对内“只学习”的原则：克制自研范围
不引入外部底座，绝不意味着无限制地扩充 `@supacloud/app`：
- **对外**：学习业界已经验证过的生命周期边界、测试场景与设计约束；
- **对内**：主动审视并收缩自研框架中非必要的抽象。不再为了“模仿大型企业框架”而增加不使用的反射容器或兼容层，坚守静态编译与执行管线的极简定位。
