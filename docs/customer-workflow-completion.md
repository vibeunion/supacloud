# Customer workflow completion

This increment connects existing application context, reference business flows
and deployment evidence. It does not introduce another framework, identity
provider, migration runner or automatic recovery engine.

## Acceptance

```gherkin
Scenario: Work on a bounded feature
  Given a declared module with separate command and aspect source files
  When an agent requests its context
  Then it receives maintained sources, reusable declarations and focused tests
  And uncovered directories and release-only checks remain explicit
  And no test or generated-file write is performed

Scenario: Repair without guessing business policy
  Given a diagnostic requiring a permission or transaction policy
  When the agent inspects the repair plan
  Then the plan requires explicit input and defaults to preview
  And release drift checks precede any intentional regeneration

Scenario: Complete a client operation safely
  Given the reference list, approval and attachment transports
  When a read fails or a write has a conflict or unknown outcome
  Then the client exposes a recoverable state with the original operation identity
  And no write is automatically retried or replaced with a new identity
  And duplicate submissions cannot invoke the transport twice

Scenario: Verify what customers install
  Given an exact published CLI version and a disposable local PostgreSQL cluster
  When published-consumer acceptance runs
  Then the application is generated by the installed CLI without workspace overrides
  And installed version identities and business evidence are reported separately
  And unavailable or failing acceptance remains incomplete

Scenario: Explain deployment and recovery
  Given a validated scope-bound deployment receipt
  When the customer requests its report
  Then failed, unknown and missing evidence is identified by component
  And read-back actions retain release and activation identity
  And code rollback never claims data restoration or authenticated smoke success
```

## Evidence boundary

Source implementation, local deterministic tests, installed published consumers,
authenticated platform acceptance, deployment and recovery are separate states.
Local signed identities are not live SupAuth acceptance. No production operation
is authorized or implied by running these local tools.

## Bounded AI workflow

Run `supacloud app context --target <module-or-symbol> --format json`.
The `workflow` object contains maintained edit files, nearby reference files,
declared dependencies, preview repair plans, focused tests and coverage gaps.
Colocation is a selection heuristic, not proof of coverage. Missing tests,
unresolved directories and release-only checks remain explicit.

Run `supacloud app doctor --target <module-or-symbol> --format json` for scoped
diagnostics. It reports omitted project diagnostics and skips extra database
and unwired-contract scans; generated drift still covers the project.
The compiler still constructs the project graph: bounded output does not claim
incremental compilation or zero project file reads.

Review `app fix --fix <reviewed-fix.json>` output before explicitly applying a
repair. Business permission, transaction and identity choices require input.
For daily work, intentionally compile and run the selected test file.
For a release, run `app check` against committed artifacts **before** any
regeneration. A failed drift check must not be hidden by auto-generating files.

## Frontend integration

The command starter emits `src/client/reviews.ts` and
`src/client/review-transport.ts`, plus a focused behavior test. No Svelte,
SVAdmin or other UI framework dependency is added.

1. Construct a user-scoped Supabase client and `createAuthenticatedFetch` from
   `@supacloud/js/contracts` using the same current session. Never use a service
   key in a browser. Configure one trusted HTTPS application origin.
2. Pass them to `createReviewTransport`, then to `createReviewClient`.
   Supply `createReviewPendingStore(localStorage, { projectId, tenantId,
   applicationId, subject })` as the client's second argument, using the current
   authenticated session and application binding. Bind `snapshot()` and
   `subscribe()` to the view or SVAdmin store.
3. Map list loading, empty, denied and error states separately. The reference
   reads the first 100 rows; production pagination is an application extension.
4. Bind approve/upload actions to the controller methods. Disable writes while
   submitting or unknown; keep the original operation ID for investigation.
   Conflict refreshes the list but does not retry the mutation.
5. `reconcile()` uses the shipped `GET /reviews/:id/operations/:operationId`
   endpoint with `kind` and `expectedVersion`. Both approval and upload lookup
   recheck the current permission and tenant/application binding through the
   original command store. Missing receipt stays unknown; denial or fingerprint
   conflict during recovery also stays unknown and does not unlock new writes.
6. Unsubscribe and dispose on logout, session identity changes and unmount.
   Do not share a client instance across users. Pending operation IDs are saved
   before dispatch, contain no token/file bytes, and survive disposal and reload.
   Corrupt/unavailable storage blocks writes; a matching confirmed receipt clears
   the record. Local storage is not a cross-tab atomic lock: use one active
   mutation owner per identity/application and never erase unresolved records
   merely to enable a new write.

The transport uploads private text attachments without overwrite and verifies
the registration's artifact, path, byte count and SHA-256. Failed or lost
responses do not trigger replay. Local port and HTTP-adapter tests do not
constitute a browser or live identity acceptance test.

Focused source verification:

```sh
cd packages/cli
bun test src/shared/tools/app-starter-client.test.ts
SUPACLOUD_STARTER_POSTGRES_BIN=/opt/homebrew/opt/postgresql@16/bin \
  bun test src/shared/tools/app-starter-recovery.test.ts
```

Install frozen dependencies in the CLI, app, elysia, commands, contracts, db,
query and supacloud-js packages first. This source-only fixture uses explicit
source paths, strict compiler diagnostics, a disposable native PostgreSQL
cluster and locally signed identities. It checks compiled GET routes, revoked
permissions, foreign subjects/tenant bindings, input fingerprint conflicts,
database restart, no lookup mutations, and a committed-but-lost approval response
followed by a reloaded client recovering the original operation. Upload receipt
lookup uses the real command store but seeds the upload receipt independently;
list refresh is stubbed in this fixture. It is not published/browser acceptance.

## Published consumer gate

Run from this repository, with explicit published versions:

```sh
bun scripts/check_published_customer.ts \
  --cli-version 0.99.0 --lite-version 0.28.2 \
  --postgres-bin /opt/homebrew/opt/postgresql@16/bin \
  --report /tmp/supacloud-published-customer.json
```

The gate installs the CLI from npm into a disposable directory, generates the
consumer with that CLI, rejects local dependency overrides, verifies a frozen
offline installation, compiles and type-checks, runs the emitted client test,
and uses the installed Lite public runtime for durable business fixtures.
It never substitutes workspace templates or runtime code. PostgreSQL is local
and disposable; no remote database URL is accepted.

The portable report records stage, selected package versions and evidence.
Failure diagnostics are in an adjacent mode-0600 `.diagnostic.txt` file;
inspect locally and redact before sharing. A cleanup failure fails acceptance.
Local signed fixture identities never count as live SupAuth smoke.

On 2026-10-15 the published `@supacloud/cli@0.99.0` run failed at
`install-consumer`: its generated `@supacloud/js@^0.42.0` dependency was not
available in npm (the queried published version was `0.41.1`). No downstream
business, browser or recovery acceptance was reached. Publish a compatible
package set through the normal release process, then rerun this gate; do not
silently downgrade the contract or inject a local package to claim success.

## Deployment and recovery report

Use `supacloud app evidence --ref <project> --id <application> --environment_id <environment>`
to read recorded evidence. Text output identifies incomplete,
unknown and failed components and the next read-back action; JSON preserves
the authoritative receipt. This operation neither deploys nor probes the live
system. Correlate release, activation and manifest identity with existing logs.

The delivery package exports `summarizeDeploymentEvidence` for customer
interfaces. Its summary excludes free-form receipt notes. Legacy v1 receipts
remain parseable; additional missing inventory, backup or rollback proof makes
the customer summary incomplete without rewriting the recorded status.

For unknown outcomes, read back the original activation/migration/operation
identity before any further mutation. Code rollback selects a release and
configuration; restoring database or object storage requires a separate
approved restore plan and recovery drill. Recheck permissions and perform
real-session business smoke after upgrading or recovering.

## Remaining acceptance

This increment is not evidence of completed platform acceptance. The published
package dependency closure must first be repaired by a release. Live SupAuth
business smoke, browser/SVAdmin acceptance, cross-component tracing acceptance
and an approved full database/object-storage restore drill remain required
before all three customer outcomes can be signed off.
