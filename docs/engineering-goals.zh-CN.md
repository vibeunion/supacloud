## 目标

让开发者与 AI 用更少的重复基础代码完成业务开发，提前获得错误反馈，
并保持明确的责任归属。衡量的是业务变更能否被验证，而非装饰器、包或生成文件数量。

四个目标：可靠基础层、便捷 Vibe Coding、类型与编译提前发现错误、
通过模块边界和静态 AOP 提高大型项目可维护性。

## 职责边界

| 层级 | 负责 | 不负责 |
| --- | --- | --- |
| SupAuth 外部统一用户中心 | 统一登录与用户中心产品集成；认证、会话和令牌签发由 GoTrue 承担 | 应用对象关系和业务流程裁决 |
| 应用框架 | `@supacloud/app` 元数据和契约、`@supacloud/compiler` 静态分析与生成、`@supacloud/elysia` 执行和适配器 | 第二套身份提供方、任意动态拦截、通用业务模型 |
| SupaCloud 平台 | 项目隔离、控制平面 RBAC、数据库和运行时生命周期、交付与运维基础能力 | 各应用成员关系和业务流程数据库的副本 |
| 业务应用 | 领域契约、权威业务关系、对象权限、状态转换和事务持久化 | 密码验证、令牌签发、重复建设统一用户中心 |

SupAuth 是企业统一身份场景的外部依赖，不是编译和本地测试的必需服务。
现有平台 GoTrue 与 Lite Auth 是独立支持模式，本契约不删除它们，也不自动迁移用户。
详见[授权边界](authorization-boundary.md)。

以下为源码中的集成点，不代表生产验收通过或新版本已经发布。

沿用现有包边界，不为满足这些目标引入聚合框架、通用工作流引擎或第二套 Schema 来源。

## 统一身份契约

企业应用接入 SupAuth 时：

1. 登录与会话处理使用认可的 SupAuth 集成；业务模块不实现密码存储、令牌签名或刷新流程。
2. 可信宿主验证凭据后才能构造请求身份。验证必须绑定配置的签发者、受众、
   允许的算法和密钥，并检查过期时间。未验证的令牌解码结果、请求体和用户自填身份头不能作为依据。
3. 将验证后的签发者和主体映射到应用本地访问上下文。统一用户不代表自动获得所有项目权限；
   共享认证的从属项目不能假设本地存在对应 `auth.users` 记录。
4. 对象关系和流程权限读取当前应用数据；平台 RBAC、令牌数据库角色与业务角色必须区分。
5. 身份无法验证时拒绝受保护访问，不回退到演示身份、本地登录或服务角色绕过。
   用户中心故障时已签发令牌是否仍可验证，遵循已配置的验证与缓存策略，不使用整体绕过机制。
6. 身份认证与业务授权分离。幂等重放也重新检查业务权限，缓存成功结果不能绕过权限撤销。

运行时提供 `createSupAuthRequestContext`，模板导出 `createSupAuthApp`，
完成签名验证与应用本地访问解析接入，详见[运行时示例](../packages/elysia/README.md#external-supauth-identity)。
本地测试使用合成密钥产生真实签名并发起 HTTP 请求；真实 SupAuth 会话和应用数据库验收
仍是部署门槛。这不代表已经安装或迁移某个用户中心实例。

## 静态 AOP 契约

仅在支持的模块、路由、命令和任务边界显式声明切面。
授权、幂等、事务和审计复用已有命令治理，不在无关切面里再造同样机制。

业务决策留在领域代码中。执行顺序必须确定、可检查，并测试提前拒绝、异常和资源清理。
切面不能重复调用业务处理器或隐式重试写操作。
事务与审计的原子性必须由持久化适配器保证，不能根据装饰器的存在推定。
响应校验可能在提交之后失败，应读取持久化回执而非盲目重试。

## 实施顺序

1. 在项目入口文档和生成模板中落实上述职责契约。
2. 补齐受支持的 SupAuth 宿主适配示例、可信身份验证、项目本地访问解析和真实认证的多应用测试。
3. 选择一个真实业务命令，联合验证持久化授权、并发、幂等、事务与审计。
4. 仅为静态可证明的错误添加编译检查、可操作诊断和反例；外部事实保留运行时校验。
5. 验证 AI 辅助功能开发与修复、多模块 AOP 行为；发现有意义的重复工作后再扩展公共能力。

## 本地实现

- 外部身份适配器：HTTPS 信任配置、非对称签名验证、本地访问解析、跨项目拒绝，不回退到转发身份头。
- 命令、事务、幂等和任务的重复调用保护，以及仅包含元数据的执行追踪；持久化适配器仍由应用提供。
- 非法命令治理模式诊断与显式语义修复；编译错误默认保留正常产物。
- 定向上下文包、切面源文件、相关诊断与静态执行计划；模板包含生产身份入口和检查修复流程。

包测试与打包后的模板验证覆盖这些本地契约，不代表真实 SupAuth 会话、PostgreSQL/RLS
保证、版本发布或生产部署已完成。上述实施顺序仍用于各真实业务应用的接入，
不要求框架重复建设领域数据库。

## 验收标准

```gherkin
Feature: 可验证的企业应用开发
  Scenario: 本地开发不依赖用户中心
    Given 新模板项目没有 SupAuth 凭据
    When 开发者执行文档中的本地验证
    Then 编译和确定性测试可以在没有 SupAuth 的情况下运行
    And 内存演示不能作为生产身份适配器

  Scenario: 统一登录不授予跨应用访问权
    Given 已验证的 SupAuth 用户仅拥有应用 A 的成员资格
    When 用户请求应用 B 的受保护资源
    Then 应用 B 拒绝访问且不产生业务副作用
    And 无法验证的凭据不会回退为演示身份

  Scenario: 权限撤销对幂等重放生效
    Given 一个成功命令回执且调用者的本地权限随后被撤销
    When 调用者使用相同幂等键重复命令
    Then 授权在返回缓存成功结果之前拒绝请求

  Scenario: 静态错误不覆盖正常产物
    Given 已有可用的编译产物
    When 变更引入无法解析的依赖或动态切面引用
    Then 编译报告能定位问题的诊断
    And 不替换已有正常生成产物

  Scenario: 切面失败不重复业务操作
    Given 显式切面链和持久化命令适配器
    When 业务操作周围的执行失败
    Then 不自动第二次执行业务操作
    And 已提交结果通过持久化回执确认
```
