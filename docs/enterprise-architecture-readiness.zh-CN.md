# 企业级架构就绪度

[English](enterprise-architecture-readiness.md) | [简体中文](enterprise-architecture-readiness.zh-CN.md)

> 状态: 基准契约
> 更新时间: 2026-10-04

本文档定义了 Pigsty 管理的节点能力与 SupaCloud 管理的平台能力之间的职责边界。一个功能不能仅仅因为存在某个命令或脚本就被视为完备；它必须拥有明确的责任主体、可逆的操作流程、可观察的结果以及验收检查手段。

具体的 Pigsty/pgBackRest 操作步骤请参见 [Pigsty 备份与恢复运维](./pigsty-backup-operations.zh-CN.md)。

## 职责边界

### Pigsty 作为基础设施底座

Pigsty 可以负责或提供：

- PostgreSQL 集群拓扑、Patroni、Leader 选举与故障转移（failover）
- PostgreSQL 主从复制、连接池、数据库扩展（extensions）及节点级性能调优
- pgBackRest 备份与 WAL/PITR 传输
- 节点级 Prometheus/Grafana Exporter 与基础设施仪表盘
- 基础操作系统/数据库配置与集群生命周期原语

Pigsty 自身并不负责以下内容：

- SupaCloud 项目与租户之间的硬隔离
- Caddy 路由、TLS、租户级限流策略与网关策略
- Management API 授权、双人审核（maker-checker）、审计日志与操作幂等性
- PostgREST、GoTrue、Edge Runtime、Realtime 与 pgredis 的生命周期协同
- 发布版本兼容性、构建产物唯一标识（artifact identity）、部署回执与回滚机制
- 跨组件请求链路追踪、平台 SLO 或面向客户的事故管理
- 对象存储持久性、Secret 密钥轮换、数据擦除与租户清理
- 完整 SupaCloud 项目的容灾恢复验收

### SupaCloud 拥有平台级契约

SupaCloud 必须将 Pigsty 视为可替换的基础设施提供方。平台契约必须能够适配受支持的 Pigsty 部署，并向上暴露提供方中立的健康检查、备份、恢复、扩缩容与故障转移状态。

## 就绪度领域清单

| 领域 | 当前基线 | 完备性验收证据 |
| --- | --- | --- |
| 节点高可用 | 具备 Patroni/HA 脚本并集成 Pigsty | 具备实测 RTO 的自动化故障转移与主备切换演练 |
| 备份与容灾 | 具备 pgBackRest/PITR 与项目级恢复接口 | 异地备份、计划恢复演练、实测 RPO/RTO 记录 |
| 可观测性 | 具备 VictoriaLogs、Grafana、Prometheus 指标、Request ID | 全链路 Trace 传递、SLI/SLO 告警规则与应急预案（runbooks） |
| 发布安全性 | 具备 SHA-256 校验、物料清单、清单清单、回滚助手 | 覆盖所有组件的一体化发布回执及经过验证的回滚流程 |
| 租户隔离 | 具备 RLS、每租户运行时、Capability 边界 | 跨租户反向安全测试与资源公平调度测试 |
| 安全合规 | 具备 TLS、Secret 文件管理、审计链路、依赖审计 | 密钥轮换演练、容器漏洞扫描、SBOM 留存、权限审计 |
| 容量治理 | 具备网关、Worker、队列和数据库治理控制 | 租户配额、嘈杂邻居（noisy-neighbor）测试、容量分析报告 |
| 数据生命周期 | 具备备份、存储和删除操作 | 保留周期合规、数据擦除、导出与无权限漂移的恢复测试 |
| 运维体系 | 具备健康检查与升级脚本 | 运维手册、责任人机制、升级上报通道、变更与故障台账 |

## 必需的 SLO 模型

平台必须至少定义并公开以下服务等级目标：

- 控制面可用性与请求延迟
- 租户 REST/Auth/Storage API 可用性
- Edge Function 成功率、执行延迟、冷启动率与队列积压延迟
- 数据库故障转移耗时与复制延迟
- 备份新鲜度、备份成功率与恢复成功率
- 日志摄入延迟与保留周期合规性

每个 SLO 都必须配备责任主体、测量指标数据源、告警阈值以及标准应急手册。没有告警和处置手册的仪表盘不属于有效的运维控制手段。

## 恢复验收标准

最小化的完整恢复演练必须满足：

1. 选取真实或具有代表性的租户数据夹具（fixture）。
2. 从独立的异地存储位置验证最新备份及其校验和。
3. 恢复数据库、对象存储、Secret 密钥与运行时元数据。
4. 对齐数据库迁移与组件版本。
5. 验证匿名请求拦截与认证请求放行的安全边界。
6. 验证租户数据隔离、活跃路由、函数执行、消息队列及审计记录完备性。
7. 记录实测 RPO、RTO、恢复操作回执及未解决的系统偏差。

单纯 `pgBackRest info` 成功或 Patroni 集群状态健康，不能替代完整的恢复验收。

## 生产发布验收标准

一次生产发布只有在提供以下全部凭据时才被视为完成：

- 不可变源码 Commit SHA 与组件版本号
- 构建产物摘要校验（digest）与来源可信验证
- 数据库与运行时的版本兼容性评估结论
- 发布前检查（preflight）生成的备份与数据库迁移清单
- 包含每个组件详细状态的部署操作回执
- 组件健康与就绪度回读数据
- 具有代表性的已认证端到端冒烟测试结果
- 明确的回滚目标版本及回滚操作回执

## Gherkin 验收用例

```gherkin
Feature: 企业级灾难恢复就绪度

  Scenario: 通过基础设施提供方完成节点故障恢复
    Given 一个由 Pigsty 和 Patroni 管理的双节点 PostgreSQL 集群
    And SupaCloud 租户运行时处于健康状态
    When 当前主节点发生故障不可用
    Then Patroni 自动选出健康的新从节点升级为主节点
    And SupaCloud 正确报告新主节点和主从复制状态
    And 实测恢复时间被记录并符合预设的 RTO 目标

  Scenario: 完整租户恢复被独立验证
    Given 某租户在异地已具备校验通过的备份数据
    When 运维人员恢复数据库、对象存储、Secret 密钥与运行时元数据
    Then 该租户以预期的组件版本正常启动
    And 已认证的业务请求全部成功
    And 跨租户的非法请求继续被严格拦截
    And 恢复操作回执中包含实测的 RPO 与 RTO 数据

  Scenario: 凭据不全的发布严禁报告成功
    Given 某个组件的部署结果呈现未知状态（unknown outcome）
    When 发布工作流对整体部署状态进行评估
    Then 该发布被标记为未完成（incomplete）
    And 针对非幂等变更严禁触发自动重试
    And 运维人员接收到故障组件标识及所需的排查回读说明

  Scenario: 单一租户无法耗尽平台共享资源
    Given 两个租户共享同一组 Edge Runtime 与网关实例
    When 其中一个租户突发请求超过其配置的并发或队列配额
    Then 该租户按策略被限流熔断或延迟入队
    And 另一租户的请求延迟与服务可用性仍维持在预定 SLO 范围内
    And 该配额超限事件可通过项目标识与请求 ID 在日志中完整溯源
```

## 实施顺序

1. 完成[自托管稳定基线](self-hosted-stable-baseline.zh-CN.md)：产品边界、一个受支持的部署组合、
   干净安装和双项目运行。
2. 完成一次有状态平台升级，明确组件边界并持久化回读结果。
3. 从批准的异地快照完成一次独立环境完整项目恢复，记录实测 RPO/RTO。
4. 建立贯穿网关、API、Worker、队列、数据库及恢复操作的统一 Trace 追踪与 SLO 度量体系。
5. 建立租户配额管控、容量报告与嘈杂邻居隔离测试。
6. 完善密钥轮换、容器镜像漏洞扫描、SBOM 归档与权限复核机制。
7. 扩大跨组件升级编排并建立经过验证的回滚流程。
8. 仅在单区域容灾恢复契约完全验证通过后，再推进多节点与多区域部署规程。
