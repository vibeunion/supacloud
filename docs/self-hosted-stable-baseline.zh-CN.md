# 自托管稳定基线

[English](self-hosted-stable-baseline.md) | [简体中文](self-hosted-stable-baseline.zh-CN.md)

> 状态：产品边界与验收契约
>
> 更新时间：2026-10-04

本文明确 SupaCloud 的主产品：

> **SupaCloud 是一个可长期维护的自托管多项目应用平台。**

用户在自己的基础设施上，通过统一控制面、控制台、运维 CLI、项目 CLI、
交付流程、可观测性、升级流程和恢复流程，运行多个相互隔离的
Supabase 风格项目。

应用框架、编译器、SDK 和 AI 工具属于可选的应用开发层，用来改善项目开发
体验和应用契约；它们不是使用平台，或部署遵循 Supabase 兼容协议的应用的前置条件。

本文是发布边界，不代表下面所有项目已经通过真实生产安装、升级或恢复演练。

## 产品层级

| 层级 | 产品职责 | 完整平台使用要求 |
| --- | --- | --- |
| Full Platform | 主产品：自托管项目控制、运行、交付、运维、升级和恢复 | 多项目平台流程必需 |
| Admin、Console 与项目 CLI | 标准运维与开发入口 | 平台不能要求用户直接访问源码 |
| 应用框架、编译器、SDK 与 AI 工具 | 可选的开发加速与应用契约增强 | 非必需 |
| Lite | 本地优先和小型单项目运行时 | 独立的有边界产品，不证明完整平台生产就绪 |

不要把这些描述成同一个框架的可互换版本。平台是产品，应用工程是其上的可选层。

## 首要支持组合

第一个稳定版本只应优先发布一个明确的部署组合：

| 维度 | 基线 |
| --- | --- |
| 主机 | 使用 systemd 的 Linux |
| 首要操作系统验收目标 | Ubuntu 24.04 LTS |
| 首要架构验收目标 | `amd64` |
| 数据库底座 | Pigsty `v4.5.0`、PostgreSQL 18 |
| 网关 | SupaCloud 管理的 Caddy systemd 服务 |
| 平台运行时 | Management API、Web Console、项目运行时和 VictoriaLogs |
| 存储 | PostgreSQL 元数据的 JuiceFS；项目显式绑定受支持的 S3 兼容后端时另行验收 |
| 制品模式 | 已发布、校验和通过且来源证明通过的 Release 制品 |
| 高可用声明 | 单机基线不声明高可用 |

安装器中的其他操作系统和 `arm64` 路径必须单独记录和测试，不能自动视为与首要
基线等价。Compose 与 Lite 按各自文档支持，不作为完整平台验收的替代证据。

首轮验收必须记录选用的 Edge Runtime 模式。Management/Web Console/Edge Runtime
协同升级要求持久化 `EDGE_RUNTIME_MODE=external`；嵌入模式不能被默认为同等升级证据。
Caddy 与 GoTrue 仍是独立的升级面。

## 支持矩阵

| 范围 | 状态 | 边界与证据 |
| --- | --- | --- |
| 原生单机 Full Platform | 稳定基线目标 | Ubuntu 24.04 LTS、`amd64`、systemd、Pigsty `v4.5.0` / PostgreSQL 18、SupaCloud 管理的 Caddy 和已发布且经过验证的制品；在声明生产验收前仍需完成第二至第四道验收门 |
| Lite | 独立有边界产品 | 单项目本地优先运行时，有自己的兼容性与恢复证据；不能证明 Full Platform 已就绪 |
| Compose 与其他安装路径 | 特定部署方式支持／需单独验收 | 遵循各自文档边界，不能作为原生基线的等价证明 |
| `arm64` 与其他操作系统 | 特定部署方式支持／需单独验收 | 必须针对选定组合提供明确的安装、升级和恢复证据 |
| 项目级外部 S3 存储 | 特定部署方式支持／需单独验收 | 需要显式项目绑定，以及针对提供方的可达性、持久性和恢复证据 |
| 有状态协同升级中的嵌入式 Edge Runtime | 实验性／需单独验收 | 首要协同升级证据使用持久化的 `EDGE_RUNTIME_MODE=external` |
| 控制面故障后的数据面存活 | 实验性目标 | 当前不作保证，必须通过故障演练实测哪些项目流量可以继续 |
| 高可用、多节点调度和多区域运行 | 单机基线范围外 | 需要独立的故障转移、容量、升级和恢复证据 |
| 应用框架、编译器、SDK 与 AI 工具 | 可选开发层 | 用于增强应用交付与契约，但不是运行平台项目的前置条件 |

“稳定基线目标”表示计划支持的发布组合，不表示生产证据已经完成。
只有相关验收门产出带日期的证据后，发布才能标记为已验收。

## 平台边界

### 控制面

控制面负责：

- 项目身份、归属、状态和资源绑定
- 项目与平台配置
- 发布与激活记录
- 操作意图、进度、结果和回查
- 备份清单、恢复计划和恢复回执
- 授权、审计和面向运维者的诊断

所有写操作应逐步统一为：

1. 校验授权和前置条件。
2. 持久化操作意图和稳定 mutation identity。
3. 只执行可安全重试的步骤。
4. 回读真实资源状态。
5. 对丢失或未知响应先回查，再允许新变更。
6. 报告成功、可恢复失败或需要人工处理的结果。

应扩展现有项目生命周期和发布契约，不要仅为了统一名称再造第二套项目账本、
源码管理系统或通用工作流引擎。

### 数据面

数据面通过网关承载项目的数据库、REST、Auth、Storage、Realtime、Functions
和 Worker 流量。

当前部分公开 Functions、Realtime 和 Storage 请求仍经过 Management API。因此，
“控制面故障时已运行项目仍可服务”是目标验收属性，不是当前默认保证。第一步应先
逻辑分离权限、连接池、并发预算和生命周期，再根据真实故障传播结果决定是否拆进程。

### 基础设施

Pigsty 继续作为数据库基础设施提供方。SupaCloud 负责项目级产品契约：隔离、路由、
运行时生命周期、跨组件交付、运维流程和完整恢复验收。PostgreSQL 高可用、pgBackRest、
WAL 传输和节点原语应通过明确的提供方契约使用，不在平台内部重复实现。

## 发布术语

| 术语 | 含义 |
| --- | --- |
| 平台发布 | Management API、Web Console、运行时制品、配置契约和组件版本组成的已验证组合 |
| 项目应用发布 | 函数、前端、运行时配置和迁移清单等不可变项目制品集合 |
| 基础设施升级 | Pigsty、PostgreSQL、Caddy、GoTrue、Realtime、存储或操作系统变更，各自有迁移和回滚边界 |
| 恢复回执 | 指定快照被恢复并验证后的证据，包含实测 RPO/RTO 与未解决偏差 |

二进制回滚不会撤销数据库迁移或外部副作用；项目恢复不等于集群 PITR；备份清单
成功也不等于恢复成功。

## 四道验收门

### 第一门：产品与支持边界

交付：

- 根 README 和文档索引中的主产品声明
- 一份标明稳定、实验、特定部署支持和范围外能力的支持矩阵
- Full Platform、Lite 和应用工程层的清晰区分
- 支持的操作系统、架构、组件固定版本和高可用限制

通过条件：新运维者能够选择正确入口，并知道哪一种部署组合可以依赖。

### 第二门：干净安装与双项目运行

使用干净主机和已发布制品，创建两个代表性项目：

1. 只使用标准 Supabase 客户端和平台接口的项目。
2. 使用可选 SupaCloud 应用框架的项目。

两个项目都必须验证：

- 项目创建失败时不会留下无法解释的半成品
- 数据库、Auth、REST、Storage、路由和 Functions 都按项目隔离
- 一个项目不能读取、路由到或修改另一个项目
- 迁移和函数发布具有不可变身份并能回读
- 日志和项目状态能呈现可诊断的失败原因
- 主机重启后平台和两个项目回到预期状态

第一个项目证明完整平台不依赖 `@supacloud/app`。

### 第三门：有状态平台升级

从上一受支持平台制品开始，保留代表性数据和配置。证据必须包含：

- 源和目标平台发布清单
- 所有组件版本和制品摘要
- 数据库迁移清单与兼容性结论
- 备份和升级前检查结果
- 每个组件的激活与健康回读
- 观察超时或中断后的处置结果
- 回滚目标以及仍需人工执行的恢复路径

首个基线可以将 Management API/Web Console 与 Caddy、GoTrue、Realtime 或
PostgreSQL 分开升级，但发布说明必须明确写出边界。

### 第四门：独立环境完整恢复

从独立于源主机的批准快照恢复到新环境，验证：

- 数据库状态以及迁移/组件版本一致性
- 对象文件和存储命名空间
- 运行时元数据、密钥和项目身份
- Auth 与授权边界
- 活跃路由和函数执行
- 快照包含的队列、日志和审计记录
- 跨项目隔离
- 实测 RPO、实测 RTO 和全部未解决偏差

合成的本地恢复夹具适合回归测试，但不能证明生产恢复保证。

## 证据状态

每份验收记录必须明确标注状态：

| 状态 | 含义 |
| --- | --- |
| 已实施 | 源代码或文档已经存在 |
| 本地已验证 | 确定性的本地测试或夹具通过 |
| Release 已验证 | 已发布制品和清单已验证 |
| 已部署 | 指定主机接受制品并回读健康证据 |
| 在线已验收 | 目标环境的已认证代表性流程通过 |
| 未完成 | 证据缺失、结果未知或流程被中断 |

不要把这些状态压成单一成熟度百分比。单元测试、合并 PR、部署和恢复演练证明的是不同事情。

## 本基线不承诺

- 所有 Linux 发行版或 CPU 架构
- 单机基线上的高可用或多节点调度
- 未经故障演练证明的控制面故障存活
- 数据库迁移或外部副作用的自动回滚
- 从集群级物理备份直接执行单项目 PITR
- 完整 Supabase Cloud 功能对等
- 强制所有项目采用 SupaCloud 应用框架
- 第二套 Git、配置、权限或操作账本

除非一个新能力明显改善安装、运行、交付、升级、恢复或已承诺的兼容性，否则不要把
新运行时、更大的框架或多集群调度加入当前主线。

## 验收场景

```gherkin
Feature: 自托管稳定基线

  Scenario: 新运维者能够选择受支持的平台
    Given 根 README 和支持矩阵已经发布
    When 运维者选择部署入口
    Then Full Platform、Lite 和应用框架边界清晰可见
    And 首要操作系统、架构、组件版本和高可用限制可见

  Scenario: 不使用应用框架也能运行平台项目
    Given 一个干净的受支持主机和已发布制品
    When 运维者使用标准 Supabase 客户端创建项目
    Then 项目可以使用数据库、Auth、REST、Storage、Functions、日志和路由
    And 不要求安装 @supacloud/app

  Scenario: 两个项目保持隔离
    Given 两个项目运行在同一受支持主机上
    When 一个项目尝试使用另一个项目的凭据、路由或存储
    Then 操作被拒绝
    And 拒绝结果带有项目和请求身份记录

  Scenario: 升级未知结果不能被报告为成功
    Given 有状态平台升级已经开始
    When 观察被中断或某组件结果未知
    Then 发布状态为未完成而不是成功
    And 运维者能够在重试前读取持久化状态

  Scenario: 完整恢复必须独立验证
    Given 一个批准的快照和新的隔离环境
    When 数据库、对象、密钥、运行时元数据和路由被恢复
    Then 已认证的项目检查通过
    And 跨项目访问仍被拒绝
    And 回执记录实测 RPO、RTO 和未解决偏差
```
